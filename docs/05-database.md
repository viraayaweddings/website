# Database Documentation

**Technology:** Neon Postgres via Drizzle ORM (`postgres.js`)  
**ORM:** Drizzle ORM 0.45  
**Schema file:** `worker/db/schema.ts`  
**Client:** `worker/db/client.ts` (auto-applies migrations on first access)

### Two migration sets, and which one runs

| Set | Applied by | Role |
| --- | --- | --- |
| `drizzle-pg/0000`–`0008` | `worker/db/apply-pg-migrations.ts` | **The live schema.** Postgres DDL, generated by `drizzle-kit` from `worker/db/schema.ts` (see `drizzle.config.ts`, `out: "./drizzle-pg"`) |
| `drizzle/0000`–`0026` | `worker/db/migrations.ts`, via `seed-content.ts` | **Content seeds only.** The original SQLite/D1 migrations, kept because the `*_seed_*.sql` files are still the source of the site's starting content |

The legacy set is not dead — `seedSiteContent` replays its seed files through
`sqliteToPostgres` — but it no longer defines the schema. Read `drizzle-pg/` to
learn what a table looks like; read `drizzle/` to learn what was seeded into it.

## Entity Relationships

```
users ──< sessions
users ──< audit_log (nullable FK, SET NULL on delete)

city_listings ──> hotels (logical: venue_city + venue_slug)
blog_listings ──> blog_posts (logical: post_slug)

hotels ──> page_templates (shell_key)
blog_posts ──> page_templates (shell_key)
city_pages ──> page_templates (shell_key)

media ── referenced by hero_slides.image_key, hotels.*_image, blog_posts.*_image (logical)
```

Only formal FKs: `sessions.user_id → users.id` (CASCADE), `audit_log.user_id → users.id` (SET NULL).

### `static_pages`

| Column | Type | Notes |
| --- | --- | --- |
| `path` | TEXT PK | No trailing slash |
| `title`, `meta_description` | TEXT | |
| `html` | TEXT | The whole page |
| `published` | INTEGER 0/1 | See below — unpublishing does not take the page offline |
| `origin` | TEXT | `STATIC_PAGE_ORIGINS` — where the row came from, so a seeded page and a hand-created one can be told apart |
| `updated_at` | TIMESTAMPTZ | |
| `updated_by` | TEXT | Editor email |

About 35 rows and 9MB, because each holds a complete page.

It holds the third kind of page. Venues, articles and city indexes are rebuilt
from a shell plus content rows; the rest of the site was served straight from
its cloned file, so nothing an admin changed reached it. These pages have no
repeating structure worth modelling — a calculator and a privacy policy have
nothing in common — so each is stored whole.

`resolvePage` checks this table **before** the pattern matches, because a stored
path is exact and `/destination-wedding-in-goa` sits close enough to the venue
patterns that order decides which wins.

Unpublishing a row does not take the page offline: it falls through to the
cloned file, which is the same page without any of the edits. That is also what
the reset action relies on.

## Infrastructure Tables

### `content_version`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | INTEGER PK | Always `1`; the table holds one row |
| `version` | BIGINT | Bumped on every content change |
| `updated_at` | TIMESTAMPTZ | |

Every content module holds a module-scope cache — 30 seconds for most of it, 5
minutes for page templates and labels. The `invalidate*Cache()` calls in a
server action clear it only in the instance that handled the save, so every
other warm instance kept serving the old content until its own TTL lapsed. An
editor's own refresh could land on a different instance and show the page they
had just changed, unchanged, which reads as "the save didn't work".

`worker/site/content-version.ts` owns the row. `publishContentChange` bumps it
after a write; `onContentChanged` registers a cache to drop. Instances re-read
the counter at most every **2 seconds** (`POLL_MS`), de-duplicated so concurrent
requests share one lookup, and drop their caches when the number has moved. The
per-module TTLs remain as the backstop — this is what makes a save visible
everywhere within the poll interval rather than within the longest TTL in the
codebase.

### `rate_limits`

| Column | Type | Notes |
| --- | --- | --- |
| `key` | TEXT PK | e.g. `login:<ip>:<email>` or `login-account:<email>` |
| `count` | INTEGER | Attempts in the current window |
| `reset_at` | TIMESTAMPTZ | When the window expires |

In the database rather than in memory for the same reason as `content_version`:
an in-process counter limits one instance, so an attacker spread across
instances is not limited at all. `worker/admin/rate-limit.ts` owns it.

Admin login counts against **two** keys, and either one throttles:

| Key | Ceiling | Window | Purpose |
| --- | --- | --- | --- |
| `login:<ip>:<email>` | 8 | 15 min | The per-address limit |
| `login-account:<email>` | 25 | 60 min | A looser ceiling on the account alone, since the per-address limit only slows an attacker who keeps one address. Set where a real person sharing an office network will not reach it |

A successful sign-in calls `clearRateLimit`.

## State Transitions

### Lead status

```
new → contacted → qualified → won
                           → lost
                           → spam
```

No enforced state machine — any status can be set directly.

### User status

```
active ↔ disabled (blocks login)
```

### Content status

```
draft ↔ published (blog_posts, hotels)
```

Draft content visible only with `?preview=1` + admin session.
